# 文档治理

产品文档由各产品自行拥有：Demo 内容在 `apps/demo/docs/content`，平台 API、SDK 和模块开发指南在 `apps/portal/docs/content`。根 `docs/` 保存架构决策、贡献规范、测试/发布策略及工程证据，不被网站构建扫描。源码附近 README 可解释本包契约，通过链接引用指南，不复制整篇内容。分类与路径见 [文档所有权](../architecture/documentation-ownership.md)。

## 分层原则

- 入门文档：帮助新成员在最短路径内跑起来。
- 站点开发文档：面向使用者解释接入流程；工程边界和关键取舍的权威定义放在根 architecture/ 与 adr/。
- 工程文档：在 engineering/ 定义贡献、测试、CI、发布与编码规范；历史计划、审计及验收只保留在工程目录。
- 模块文档：描述业务模块的页面、API、权限、数据模型和边界规则。
- 运维文档：描述本地开发、CI/CD、FC3 部署、环境变量和排障流程。

## 单篇文档建议结构

模块类文档建议包含：

```text
# 模块名称

## 适用范围
## 页面入口
## API 与服务
## 权限点
## 数据模型
## 关键业务规则
## 常见问题
```

架构类文档建议包含：

```text
# 主题

## 背景
## 当前实现
## 设计约束
## 影响范围
## 后续演进
```

## 维护要求

- 涉及路径、命令、路由、环境变量、部署流程的变更，应同步更新文档站。
- 明确区分“当前实现”和“规划中能力”。规划内容应标注状态，避免误导使用者。
- 避免写入个人机器路径、固定测试账号、密钥、AccessKey、数据库连接串等敏感或不可复用信息。
- PR 中如果修改 API、菜单、部署、插件 manifest，应检查对应文档是否需要更新。
