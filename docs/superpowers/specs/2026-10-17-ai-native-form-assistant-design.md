# AI 业务助手：当前界面与原生表单协作方案

日期：2026-10-17

阶段：设计评审；尚未实施

首期范围：Demo Admin 创建系统用户

## 1. 产品目标与最终选择

用户随时唤起全局助手，用自然语言说明意图。助手识别当前页面与正在编辑的表单，整理信息后自动打开原有“新建用户”弹窗并预填。用户检查、修改、填写密码，最后亲自点击原有“确定”按钮完成创建。

主交互是“全局悬浮助手 + 当前页面感知 + 原生表单协作”。聊天用于解释、追问、候选选择及结果反馈；不在聊天里另建一套完整用户表单。

本方案替代此前以聊天表单卡片为主要预览入口的设想。持久化草稿是底层恢复、版本和提交协调能力，不增加用户必须经过的中间页面。

## 2. 已调查的现有架构

| 领域 | 现有实现 | 复用与调整 |
| --- | --- | --- |
| 全局助手 | `apps/demo/admin/src/modules/ai/AiChatHost.tsx`，Provider 持有唯一聊天状态，浮窗与全屏互斥 | 保留宿主及会话引擎，增加当前页面/表单上下文 |
| 浮层 | `floating/AiFloatingPanel.tsx`、`AiFloatingLauncher.tsx` 当前均为 z-index 900 | 当前会被业务 Modal 遮罩覆盖；统一处理层级、焦点和点击 |
| 工具注册 | `packages/core/api/src/ai-capability-catalog.ts`，运行时显式注册 | 增加只读/准备能力强制边界，不开放业务提交能力 |
| 工具执行 | AI 模块 `services/ai-execution-chain.ts` | 复用权限重算、PAT 范围、数据范围与审计 |
| 用户预填 | System API 的 `prepare_create_user` 返回 `form.prefill` | 改为可持续合并的草稿，读取真实字段定义 |
| 前端预填 | System Admin `ai-prefill`、`AiPrefillGate` | 现状是一次性内存暂存、点击卡片后打开表单；升级为当前原生表单协作，避免平行实现 |
| 用户表单 | System Admin `pages/user/components/UserForm.tsx` | 手动新建与助手打开共用同一表单实例、字段、选择器和校验 |
| 业务创建 | 原有 `POST /api/v1/admin/user` → `UserService.createUser` → `UserRepository.createInTransaction` | 保留 API 与服务主链，补充共享授权校验和提交幂等 |
| 身份 | `AuthProvider`、JWT/PAT、RBAC、`establishDataScopeFor` | 沿用当前认证身份与有效权限，不另建 AI 身份体系 |
| 会话与审计 | AI 模块已有 `ai_conversations`、`ai_messages`、`ai_audit` | 新增本模块草稿迁移；复用消息与审计关联；现有系统审计插件主要输出日志 |

已发现规则不一致：AI 预填把用户名、姓名、手机号都视为必填；真实创建 Schema 要求手机号和密码，用户名、姓名可选。手机号和密码的前后端校验也不完全一致，应在原有用户创建链内统一，不能只在 AI 路径修补。

## 3. 核心使用流程

### 3.1 从用户列表发起

1. 用户唤起助手：“创建张三，手机号 13800000000。”
2. 助手读取创建用户的字段定义及当前可操作范围，保存已明确的非敏感字段。
3. 有部门、角色歧义时，用真实且可关联的候选选项询问，不自行选取。
4. 本轮信息整理完成后自动打开原有新建表单，显示已提供内容；不要求再点击聊天卡片。
5. 缺失项可以在对话补充，也可以直接在表单填写。无需为了等齐字段一直阻止打开表单。
6. 用户核对、填写密码并点击“确定”；创建成功后关闭表单、刷新用户列表，并在助手中反馈真实结果。

### 3.2 表单已经打开

助手优先绑定已打开的“新建用户”表单，不创建第二个弹窗。用户说“手机号改成……”时，只修改所指字段；手动编辑与助手修改进入同一份表单数据。

已打开编辑用户表单时，不把创建意图写入编辑表单。存在其他未保存表单时，先让用户选择保留当前编辑或切换操作，不能静默关闭、覆盖。

### 3.3 当前不在用户管理页

明确的“创建用户”请求可在不存在未保存编辑时导航到用户管理并打开原有表单。存在未保存内容时先处理切换冲突。仅有“帮我改一下”等含糊请求时，依据当前可协作对象澄清，不自动猜测目标。

## 4. 悬浮助手与业务弹层共存

- 对具有助手权限的用户，入口位于业务 Modal、Drawer 及其遮罩上方，始终可唤起；面板关闭后入口仍保留。
- 面板是非模态浮窗，不增加覆盖全页的第二层遮罩。可收起、拖动，位置限制在可视区域内；只在面板标题栏拖动。
- 不遮住业务表单主要操作区；屏幕空间不足时可收起助手继续填写，再随时唤起。首期以桌面后台为验收对象。
- 浮窗与全屏继续使用现有同一个聊天状态，不新增第二个助手实例。
- 面板明确显示“正在协助：新建用户”等上下文，切换页面或表单后及时更新。
- 统一处理层级与挂载容器，覆盖助手内下拉选项、Tooltip 等弹层。不能仅提升入口 z-index。
- 协调参与协作的 Modal 焦点管理，使表单与助手输入框均可点击、输入及键盘访问；不全局关闭所有弹窗的焦点保护。
- Esc 只处理当前获得焦点的界面层；关闭助手后将焦点返回业务表单，不连带关闭未保存表单。

## 5. 页面与表单协作契约

前端通过显式注册的页面/表单适配器开放有限能力：识别业务目标、读取允许的非敏感字段、打开原生表单、应用字段补丁、通知用户保存或取消结果。

适配器不开放提交、删除、审批或任意代码执行能力，不读取密码控件，不依赖 CSS 选择器、屏幕识别、模拟鼠标或通用 DOM 操作。

首期仅注册 `system / user.create`。助手入口可以全局可用，但未接入的页面必须说明暂不支持，不能声称可以操作所有界面。后续按真实业务需要逐个接入，避免建立通用自动执行框架。

页面上下文只携带必要的目标标识、表单实例标识、允许的字段与版本，不把整个页面 DOM、用户列表或其他无关数据发送给模型。此上下文只是交互定位信息，不构成后端授权。

表单内部继续拥有开关、表单实例、加载与提交生命周期。通过公开的协作契约接入，不把 form 实例、setter 和 loading 状态暴露给模型或业务父页面。

## 6. 字段修改与单一数据来源

- 表单打开时，当前 React 表单是可见编辑值的唯一来源；服务端草稿是带版本的恢复快照，不建立第二套独立可编辑状态。
- 记录字段修改来源：助手填写、用户手动编辑。助手默认补充空字段，保留未提及字段。
- 覆盖用户手动改过的非空字段前，展示原值与拟修改值并让用户确认；明确说“把手机号改为 X”可视为授权该次明确字段修改。
- 助手输出基于表单实例和版本应用。期间用户修改了相关字段、表单关闭或目标改变时，不自动套用过时结果。
- 手动修改的非敏感字段按字段变化合并到草稿，避免每次输入都触发模型请求；发送下一轮消息前保证上下文使用最新已同步版本。
- 保存冲突时保留本地输入并展示差异，由用户选择；不静默覆盖其他标签页或对话中的更新。
- 用户名、姓名是否必填取自真实表单定义；默认性别、状态沿用原有后台默认值，不由模型臆造。
- 密码仅保留在受保护的表单控件和本次认证提交请求中，不进入草稿、聊天历史、工具参数、模型上下文、遥测或审计正文。

## 7. 真实表单定义与候选选项

System 域以真实创建 TypeBox Schema 为字段约束来源，补充有限的字段标签、敏感属性、选择器类型和编辑能力描述。普通用户表单与助手读取同源规则，不由模型生成业务校验规则。

部门与角色选项使用共享、受当前操作授权约束的业务候选能力。保留现有部门树和角色选择控件，调整其数据来源；不为 AI 新建一套选项权限系统，也不额外要求无关的完整配置管理权限。

手机号格式与密码强度校验在原有 Schema、表单和服务之间对齐。手机号不能在 AI 路径单独增加国家/地区假设；采用原有产品手机号契约，完善其明确的格式校验，实施前检查既有数据和测试兼容性。

唯一性等服务端校验失败返回可理解的原因，保留字段。草稿预校验可以查询唯一性，但提交必须重新校验，预校验通过不保证最终可创建。

## 8. 已由用户确认的授权规则

### 8.1 角色分配

普通管理员仅能分配权限码和数据范围均不超过本人有效权限的角色。超级管理员可分配全部角色；是否具有超管能力按当前请求有效权限判定，保留 PAT 收窄语义。

权限码比较之外，按每个涉及数据范围的操作计算候选角色实际授予目标用户的范围，并与操作者该操作的授权范围比较。使用目标用户拟关联部门计算部门型范围；不能只比较 dataScope 数字。无法证明包含关系时拒绝。需要同时评估所选角色组合，不能仅分别验证单个角色而忽略组合产生的扩大。

### 8.2 部门关联

按 `system:user:create` 对应的现有数据范围解析可选部门：全部范围允许不选部门；受限管理员至少选择一个范围内部门，且所有关联部门均须在范围内；仅本人范围禁止创建。候选部门必须真实存在且处于可用状态。

### 8.3 统一执行

候选展示、草稿校验与最终提交复用同一套 System 域业务授权规则。普通后台新建也执行这些规则，不能只限制 AI 路径。身份来自 AuthProvider；权限加载和数据范围解析沿用现有体系，不信任模型或客户端传入的 actor、权限或部门范围。

## 9. 草稿持久化与状态

AI 模块新增 `ai_` 前缀草稿表及显式迁移，保存 draftId、ownerId、conversationId、module、action、schemaVersion、formData、missingFields、validationErrors、draftVersion、status、expiresAt、时间及操作结果引用。

有效期默认自创建起 24 小时，不因每次编辑无限续期。`ready` 表示可由对话收集的必要信息已齐全；密码等受保护字段仍由最终表单验证。

状态包括 collecting、ready、previewing、submitting、completed、failed、cancelled、expired。表单打开进入 previewing，不意味着字段全部合法；保存状态和校验结果分别表达不同信息。

所有读取、修改、取消与提交都验证当前用户与会话归属。取消或完成的草稿不能由迟到的工具结果重新激活。会话删除后按本模块关系清理草稿，审计按既有保留策略保留；正在提交时拒绝删除关联会话。

历史消息只携带草稿引用和结果摘要，展示时读取当前草稿状态。刷新后可以提示“继续填写”，用户主动恢复；不自动打开历史表单，更不能自动提交。

## 10. 工具边界与人工提交

工具注册、模型工具清单和唯一执行入口均只允许 read / prepare 能力，拒绝 write / sensitive。只读和草稿准备能力允许读业务数据及写临时草稿，不允许产生持久化业务变更。风险声明之外还需审查具体能力实现，不把分类本身当成全部安全保证。

自动打开、填写表单属于允许的前端协作动作；业务提交不属于模型能力。聊天中的“直接创建”“我确认了”不能调用表单 submit 或构造业务创建请求。

用户在原有 UserForm 点击“确定”时，前端先完成表单校验、同步非敏感修改并锁定精确草稿版本，再以当前身份调用原有用户创建 API。该接口增加可选的草稿提交关联信息，普通创建请求保持可用；最终业务逻辑仍走 UserService。

后端依次检查认证、创建权限、草稿归属/有效期/版本、字段合法性、部门与角色授权、唯一性及现有扩展校验，再执行创建。客户端的 `confirmed: true` 不作为授权证明。

## 11. 幂等、事务与结果一致性

同一草稿最多完成一次用户创建，提交中的草稿不可编辑。幂等由服务端数据库约束和事务实现，按钮禁用只是交互辅助。

业务创建、提交成功回执与草稿成功状态应在同一事务中提交。通过有限的公开提交参与接口传递事务，使各模块 Repository 各自操作自己的表；AI 模块不导入 System 私有实现或直接操作 sys_*，System 不依赖 AI 模块。原有 UserService 负责业务校验和创建协调，Repository 保持数据库操作归属。缓存刷新和生命周期通知在提交后执行。

事务内校验版本并锁定草稿，一次成功后重复请求读取既有结果引用。审计成功记录与提交结果协调保存；审计或网络响应异常不能把已创建业务误报为“可以重新创建”。不存密码原文或密码派生摘要作为幂等依据。

明确的校验/业务失败回滚创建，保留可编辑草稿。响应丢失时先读取服务器草稿状态：成功则展示成功，提交中则继续查询，明确失败后才允许用户再次点击。模型和客户端均不自动重试创建请求。

并发请求携带旧版本时返回冲突；重复点击同一版本只产生一次有效创建。进程异常时以数据库事务与持久化回执恢复，不依赖内存锁或超时后盲目重试。

## 12. 首期范围与兼容性

首期实现用户列表发起创建、已打开新建表单的持续协作、全局浮层共存、草稿恢复、人工提交及失败处理。保留既有全屏聊天入口，但本期原生表单协作以浮窗模式展示，避免全屏遮住待核对表单。

不实现用户修改/删除、不生成任意业务表单、不引入完整 A2UI 渲染器、不建设通用 Agent 执行框架，也不借此重构无关模块。现有其他预填能力保持人工保存边界。

需要注意的兼容性影响：普通后台新建用户也将执行已确认的部门/角色授权规则；以前可提交的越权关联会被拒绝。新增草稿迁移必须显式应用；API 契约变化后重新生成并提交 OpenAPI 客户端与类型。

## 13. 实施顺序

1. 统一真实用户创建规则，补齐共享部门/角色授权和候选查询，建立服务端测试。
2. 建立页面/表单协作契约，复用同一 UserForm，完成助手浮层和焦点共存。
3. 建立草稿存储、迁移、版本、恢复及只读/准备工具强制边界。
4. 接通多轮草稿与当前表单，处理字段来源、冲突和迟到结果。
5. 为原有创建链增加草稿关联、事务回执和幂等，接通结果反馈与审计。
6. 完成端到端验证并记录实际结果，未运行的检查明确说明。

以上为实施分解，不代表已完成；具体任务计划在设计评审后编写。

## 14. 验收与验证

| 场景 | 必须观察到的结果 |
| --- | --- |
| A：一次提供完整非敏感信息 | 自动打开原有新建表单并预填，仍需手动填写密码和点击确定 |
| B：只提供部分信息 | 多轮保留已知字段，不臆造部门/角色；可提前打开表单手填 |
| C：用户修改预填字段 | 提交使用最终表单版本，旧工具结果不能覆盖 |
| D：聊天要求跳过确认 | 不发生业务创建，不调用表单提交 |
| E：没有创建权限 | 工具和提交均拒绝；草稿不能恢复已回收的权限 |
| F：创建接口失败 | 保留输入与明确错误，无自动重复创建，可编辑后人工重试 |
| G：刷新会话 | 未过期草稿可主动恢复，不自动打开或提交，不恢复密码 |
| H：重复点击确认 | 同一草稿只创建一次，读取同一结果 |
| 已打开新建表单 | 助手操作当前表单，不出现第二个新建弹窗 |
| Modal/Drawer 打开 | 助手入口可点击，面板和表单均可输入；下拉选项及键盘焦点正常 |
| 上下文变化 | 页面切换、关闭表单、切换账号后的迟到结果不应用 |
| 授权边界 | 跨用户草稿访问、越权部门、角色权限或范围扩大均被拒绝 |
| 版本/有效期 | 旧版本、过期、取消或完成草稿不能再次提交 |
| 响应丢失/进程异常 | 查询真实结果或恢复事务状态，不盲目再次创建 |

采用分层验证：业务授权与事务测试、Fastify 路由与工具链测试、表单/状态组件测试，以及真实浏览器的浮层焦点和完整创建链路检查。涉及数据库事务与多实例幂等的断言必须有真实数据库集成验证，不能仅凭内存替身宣称通过。

实施后运行相关聚焦测试、Admin lint/typecheck/test/build、API test/build、边界检查及 OpenAPI 生成验证；按影响范围扩展仓库检查。本阶段仅编写设计文档，未执行实现验证。
